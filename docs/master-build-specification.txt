01 · DIRECTIVA EJECUTIVA
Qué se va a construir

AUREX OS será el sistema operativo interno de AUREX BI Solutions. No debe ser un dashboard aislado ni un CRM pegado a un gestor de tareas: debe ser una plataforma transaccional, analítica y colaborativa donde cada dato operativo importante nazca una sola vez, tenga propietario, historial y trazabilidad, y alimente los KPIs ejecutivos en tiempo real.

Regla central de producto
Cada módulo debe existir porque soporta una decisión, un proceso o una obligación real. “Decisión, no decoración” será también la regla del software.
Cloud-first y multiusuario: acceso seguro desde navegador, diseño responsive y permisos por rol.
Una sola fuente de verdad: clientes, oportunidades, proyectos, tareas, horas, gastos, facturas, pagos, campañas y métricas se relacionan en la misma base.
Operación + BI: toda captura operacional debe desembocar en métricas útiles; toda métrica debe permitir bajar al registro que la originó.
Automatización progresiva: primero procesos confiables; después integraciones y automatizaciones; finalmente IA sobre datos limpios.
Construcción modular: lanzar un núcleo sólido y expandirlo sin reescribir la plataforma.
Auditable: cambios críticos, estados, permisos y acciones financieras deben dejar registro.
Nombre de trabajo
Nombre principal: AUREX OS. Codename opcional para repositorio y despliegues: AUREX NEXUS. El nombre comercial puede cambiar sin alterar la arquitectura.

Las animaciones son una capa de marca, nunca una dependencia funcional. La aplicación debe seguir siendo rápida con animaciones desactivadas. El objetivo de experiencia es navegación instantánea entre vistas frecuentes, skeletons útiles, carga progresiva y tablas virtualizadas cuando existan miles de registros.

Todas las entidades de negocio llevan id UUID, created_at, updated_at, created_by y, cuando aplique, soft delete/archive.
Eventos críticos usan tablas de historial, no solo el “estado actual”.
Moneda y zona horaria explícitas; guardar timestamps en UTC y mostrar en zona del usuario.
Importes como decimal/numeric, nunca float.
Catálogos configurables para sectores, servicios, razones de pérdida, categorías de gasto y estados especiales.
Archivos en storage; base guarda metadatos, permisos, hash, relación y versiones.
Nunca guardar tokens OAuth en tablas accesibles al cliente; usar vault/secrets del servidor.

19 · DEFINITION OF DONE

CRUD funcional con validaciones y permisos reales.
Migración SQL y seed reproducible.
Estados loading / empty / error / permission denied diseñados.
Responsive desktop-first y usable en tablet/móvil para tareas esenciales.
Audit events para acciones críticas.
Métricas o eventos necesarios para KPIs instrumentados.
Unit/integration tests en lógica crítica y Playwright en el happy path.

Feature flags para integraciones incompletas o beta.
